# Sui Regulator（司岁台）整体框架与 Astra 迭代任务书

**文档性质：下一轮迭代的设计基线与执行要求，不是已完成的实现报告。**

本次核对的代码基线：`RabbitEG/sui_regulator` 的 `30f0242ba4675d5261adf8cf0e744196543b7ae8`。Astra 开始实施时必须重新检查工作区和远端，不得假定该提交仍是最新，也不得覆盖并行开发者的改动。本次梳理阅读了仓库实现和官方参考文档，未重新运行项目测试，未连接真实 GLM 环境。

## 0. 最高层原则

> 用户定义目标与授权，Sui Proxy 理解任务并决定怎么做，Candleholder 保证任务承载、代理接续、执行记录和控制边界可靠。
>
> 框架管理执行条件，不裁判工作内容；保护任务连续性，不保证模型一定作出正确判断。

必须同时满足两个方向，不能只取其一：

- 不因实验失败、测试失败、结果不理想、重复尝试或暂时没有可观察进展，就替代理停止、换方案或结束任务。
- 不因“内容由代理判断”，就取消持久化、所有权、命令回执、明确授权、外部副作用核验和用户停止权。

“能持续”不是“永远占用一个 Session”，“安全”不是“遇错就等人”，“完成”不是“所有指标都成功”。

## 1. 项目定位、目标与非目标

### 1.1 定位

司岁台是面向不稳定 AI 会话和不稳定执行环境的、任务中心的长期 Agent 运行与接续框架。

它以独立、确定性的 Python 控制程序为主轴，管理可替换的 AI 会话。研究、开发、运维和数据处理都可以是 Task；科研实验只是目前的重要应用实例，不是核心框架的内置业务类型。

Sui Regulator 是系统整体名称，不是第四个负责思考的 AI。Candleholder 是其中控制、监控与恢复职责的承载者；Controller 可以继续作为其工程实现名称，不必为了命名再拆一个服务。

### 1.2 核心目标

1. **任务连续性**：Session 崩溃、流中断、上下文耗尽、Controller 重启，不抹掉用户要求、已完成工作和接续所需事实。
2. **代理自主性**：授权范围内的分析、调试、试错、选方案、选择执行资源和完成判断由代理承担，框架不规定固定工作流。
3. **控制可靠性**：用户指令可查询、可追踪；Hold/Cancel 不被自动恢复覆盖；过期代理不能通过受管接口继续发起操作。
4. **事实可区分**：用户意图、代理声明、运行时观测分别保存；展示来源、时间和未知范围，不把模型自述当实测。
5. **接续不重做**：换代理不等于重跑已经提交的工作；身份稳定、回执持久、结果不明先核验。
6. **人和外部 AI 都能使用**：结构化 API 与 Console 面向同一组能力和同一份账本，便于远程读取、补充指令和追踪结果。

这些目标是运行时的保证范围，而不是“模型必然完成所有任务”的承诺。

### 1.3 本轮明确不做

不建设科研结论评分器、通用语义进展评分器、强制调试流程、默认第二个裁判 AI、大型多智能体组织、集群资源调度器、通用 W&B 替代品或全自动基础设施修复平台。

不强制每个 Task 都有 Experiment、训练指标、自动验收脚本或者固定成功阈值。用户有明确要求时，代理当然应遵守；框架不自行追加这些要求。

不更换 SQLite/Controller/Yan 架构去套大型编排框架；参考成熟项目的职责分离，而不是照搬其全部机制。

## 2. 各方职责与授权边界

| 主体 | 决定什么、负责什么 | 不负责什么 |
|---|---|---|
| 用户／经明确授权的委托方 | 目标、约束、权限、可用环境、停止条件、预算与追加要求 | 不必逐次批准授权范围内的正常调试 |
| Yan（大炎） | 接收和鉴别指令、记录来源、持久化、查询、回执、远程控制入口；服务人和外部 AI | 不是另一个隐藏的任务规划者；不将日志升级为用户命令 |
| Sui Proxy（岁兽代理人） | 理解完整要求，研究、编程、调试、分析结果，选择下一步和授权资源，判断内容性完成，报告和交接 | 不篡改权威要求，不自授权限，不伪造运行事实，不以声明解除执行保护 |
| Candleholder（秉烛人） | 管理 Task 的运行资格与 Session 接续；检测运行故障、核验所有权、执行恢复、持久化、唤醒和停止边界 | 不决定实验值不值得做、指标够不够好、应换哪种算法、工作是否有学术价值 |
| Runtime Adapter／执行接口 | 将 CLI/运行时事件转换为受约束的结构化事实，启动/回收受管代理，提供真实支持的工具能力 | 不声称支持未验收的平台能力；不通过自由文本猜测远端副作用 |
| Runner／外部操作适配器 | 在支持范围内执行、登记、查询和回报具体操作；维护稳定执行身份 | 不根据退出码推导整个 Task 的语义结果 |
| 账本与证据存储 | 保存 Task、指令、代际、操作回执、事件、交接和来源，支持重启恢复和分页查询 | 存储本身不是裁判，也不赋予写入内容新的授权 |
| Yan Console | 如实呈现上述状态与证据，提供与 API 一致的操作 | 不拥有额外控制逻辑，不把缓存显示成实时、不把“已记录”显示成“AI 已完成” |

### 2.1 外部 AI 的位置

Astra、其他外部 AI 或自动化客户端可以通过 Yan 作为经授权的操作者介入；它们不是核心框架内隐含的“最高裁判”。权限只来自已有用户授权。

同一个模型担任开发者、操作者或 Sui Proxy，是不同角色，不能因为模型名称相同就共享权限。Sui Proxy 不能调用操作者权限给自己的未知操作无证据放行。操作员在创建任务或修改策略时可显式选择 trusted，预先授权代理自主核验与继续执行；核验保留为代理声明，不改写 Observed State，见 [信任模式](TRUSTED_AUTONOMY.md)。

### 2.2 不取消内容判断，而是放对位置

框架可以记录“命令退出码为 1”“返回了 401”“进程身份已变化”“某个验证模板未通过”。

代理决定“这是预期负例”“值得再次复测”“应修改代码”“应换另一台授权机器”“这份证据足以回答问题”。

用户明确配置的机器验收条件可以由框架执行，这是执行任务契约，不是框架临时发明业务标准。配置之外的质量要求不得自动追加。

## 3. 核心对象与生命周期分离

以下是概念模型，不要求为了概念完整立即新增同名数据库表。

### 3.1 Task：持续的用户委托

保存完整任务原文、追加指令与版本、项目上下文、授权范围、执行能力、明确预算、用户期望状态、当前代理、接续资料与完成记录。

Task ID 跨 Session 保持稳定。模型失败次数、Session 个数和某次实验结果不能直接终结 Task。

有限任务和持续服务都应能表达。不要靠猜测自然语言给持续任务自动加终点；用户约定“持续巡检直到取消”，一次巡检成功不是整体完成。可以先用现有任务契约明确表达，不强求本轮新增复杂任务类型系统。

### 3.2 Sui Proxy 与 Session：可替换的执行者

Sui Proxy 是具有 Task 所有权的代理实例，Session 是底层模型/CLI 的会话。两者在当前 Adapter 中可以一一对应，但不要把它们的身份和 Task 混为一体。

每次接管递增 generation；同一 Task 默认只有一个被授权的活动代理。所有受管修改和启动操作必须校验代际与所有权。不同 Task 同时操作同一项目的问题，不能靠单 Task 的 lease 自动解决；部署应隔离工作目录，或明确配置冲突保护。

### 3.3 Operation／Attempt：一次动作和一次尝试

区分“同一动作的请求因网络重复送达”和“代理有意再次尝试”。前者应幂等，后者在授权范围内应允许。

幂等键绑定稳定动作身份及参数，不绑定 generation。相同键携带不同参数应报冲突；重复实验应产生新的显式尝试身份，而不是被全局去重误伤。

### 3.4 Job：独立的长期执行

Job 可以比 Session 活得更久。换代理、停止 Console 或重启 Controller，不应自动等于杀掉已脱离会话运行的工作。

必须区分托管 Job 和仅登记的外部工作。登记 PID、远端 ID、日志路径，不等于框架已拥有远端生命周期控制，更不等于提供 exactly-once。

当前仓库明确只有合成 Runner 的托管保证；真实 Bash/SSH 任务需要按实际适配能力展示保证范围。[R1][R2]

### 3.5 Observation、Incident、Handoff、Completion

Observation 是观察；Incident 是检测出的运行事件及处理证据；Handoff 是代理交接笔记；Completion 是代理针对当前任务要求提交的完成申请与框架接纳回执。

Observation 不必升级成故障，Incident 不必升级成隔离，Handoff 不会自动成为实测，Completion 的被接纳也不是科学结论认证。

## 4. 三类状态、三个不同问题

### 4.1 状态来源

- **Desired**：用户或经授权操作者希望系统怎样运行，例如继续、暂停、取消。
- **Declared**：代理报告正在做什么、如何解释结果、计划如何推进。
- **Observed**：程序实际观察到的进程、连接、文件、退出码、任务句柄、回执和指标。

每条重要事实保留来源、时间、关联身份与观测范围。三者有分歧时分别展示，不能悄悄覆盖成一个“正确状态”。

### 4.2 不混为一个绿灯

1. 代理运行时是否健康。
2. 外部操作实际执行到了哪里。
3. 工作内容是否满足用户目标。

前两项可以在证据覆盖范围内由框架观测；第三项原则上由代理判断，或由用户明确配置的验收条件辅助判断。

心跳正常不代表模型有有效输出；模型有输出不代表事情在推进；有运行指标不代表科研方向正确；某次实验成功也不代表整个 Task 完成。

### 4.3 “已核验进展”的用词收敛

当前实现将 Runner step 和批准命令的新结果记录为 verified progress。[R2] 下一轮必须说明这里核验的是运行证据，而不是工作价值。

界面优先展示“最近观测到的运行变化／证据更新时间”，代理对业务进展的解释单列。缺乏新证据只说明框架没看到，不应被翻译成“毫无进展”。

15/60 分钟等窗口可以是可配置观测提醒，但不能隐式变成失败、强制换方案或强制换代的条件。

## 5. 正常运行、等待与接续

### 5.1 新任务

Yan 接收完整要求和授权，形成持久 Task；Candleholder 分配代理；代理先了解现有环境和已有工作，再自主组织任务。

执行模式必须匹配工作：不能把只读 managed 模式启动成功展示为“正在修改代码”。需要原生执行时由用户明确选择 `claude_code`，保持现有授权边界。

### 5.2 执行中

代理通过统一协议报告当前目标、已做动作、关键证据、已有操作身份、阻塞与下一步。报告应在关键边界及时落盘，不要求每个 token 都上报，不用报告频率代替工作质量。

后台工作状态变化、工具结果、追加指令和恢复结果需要可靠地进入代理可读上下文。仅仅写入日志不等于代理已经收到。

### 5.3 等待也是合法执行状态

代理可以判断应等待作业、资源、外部依赖或用户授权。等待需说明对象和再次检查的时机/条件。

框架负责按已登记条件或时间唤醒，而不是每秒重建一个模型 Session。没有活动代理的等待 Task 应仍能说明为什么在等、下一次检查是什么。

“等待一个明确条件”与“无限闲置无后续动作”不能在 UI 中混淆。唤醒机制可以复用现有轮询、协议或 Adapter，不强求本轮引入新队列框架。

### 5.4 合作式换代

guarded 模式的健康代理达到 Session 年龄后，只请求交接；trusted 模式不按年龄请求交接，正常轮次与定时等待保留当前会话。代理可以完成慢速动作，在安全边界交接；不能因为固定年龄或 grace 到期就打断正常工作。

Session 自然结束、回合预算到达，而 Task 尚未完成时，应有明确的接续或等待路径，不把自然结束记成内容失败。

真实运行故障仍允许撤销旧代并换新 Session。旧代理无法写 Handoff 时从已持久资料接续，不以缺少完美摘要为由永久停止。

### 5.5 换代后的第一件事

新代理读取完整要求与最新变更，检查上代工作记录及未决动作，核验已存在的外部作业，然后决定下一步。

不能因新开 Session 就默认重新初始化项目、重装环境、重新提交训练，或把任务缩减成“监视状态”。

## 6. 恢复策略：持续履职，限制请求速率

### 6.1 故障分类

| 情形 | 默认处理 | 不允许的推导 |
|---|---|---|
| 测试失败、实验失败、指标未达标 | 将结果完整交给代理，自主调试或得出结论 | Task 失败／完成；Session 必须换代 |
| 同样命令多次得到同样错误 | 提供可追踪的重复结果提示 | 第 N 次强制换方案或停止 |
| 严重生成重复、连续无效工具帧、进程崩溃、确认的断流 | 使用确定性规则记录证据，按策略恢复代理 | 整个用户目标不可完成 |
| 模型服务 429/503、暂时网络失败 | 限流、带抖动退避、到期探测后继续 | 超过两次就永久等人工 |
| 执行机器资源不足、项目依赖错误 | 结果交给代理，授权内诊断、替代或等待 | Controller 自动选机器或乱改环境 |
| 明确凭据被拒绝、运行时能力缺失 | 给出具体配置阻塞与恢复条件，不猜凭据 | 通过无限重建绕过权限要求 |
| 外部操作结果不明 | 核验和限制可能冲突的副作用，保留诊断通道 | 未发生、失败、可安全重发 |
| 身份冲突、所有权不一致 | 阻止冲突操作，必要时隔离并明确处理路径 | 按名字扫杀不属于本系统的进程 |
| 用户 Hold/Cancel | 持久执行该意图 | 恢复定时器自行重新启动 |

检测器应处理结构化运行事件和可复现的故障模式，不要求 LLM 理解整段聊天后再决定是否存活。会话记录仍可供人和代理阅读，但不是“语义裁判”的入口。

### 6.2 三种预算

**业务试错次数**：框架默认不设上限，由任务要求与代理判断决定。

**恢复／请求速率**：限制一段时间内请求、重建和探测的频率；达到窗口上限进入可自动退出的冷却，不永久结束 Persistent Task。多个 Task 共享同一故障服务时，应避免各自高速重试叠加；能先复用已有机制就不要引入复杂调度器。

**明确的资源额度**：只实施用户明确配置且实际可计量的限制。代理墙钟时间、token、加速卡时间、实际费用不同，不能混叫“成本”。计量覆盖不足必须说明。预算耗尽不代表工作失败，外部长期 Job 是否停止要看另行明确的授权。

### 6.3 隔离的定义

`QUARANTINED` 是保护状态，应用于身份、权限或副作用一致性等不能安全接管的问题，不应成为“错误很多”的同义词。

每次进入不可自动继续的状态，必须给出原因代码、关联证据、受影响范围、解除条件和可用动作。

暂时服务不可用要退避后再探测；不把可恢复故障伪装成永久等待。“无限持续”是持久承载与周期尝试，不是无延迟重试风暴。

## 7. 未决操作：保护应可恢复，不应锁死排障

### 7.1 首先区分三件事

- **命令调用返回了什么**：调用已返回、给出后台 handle，还是连接丢失。
- **工作当前处于什么执行状态**：排队、运行、停止、退出。
- **外部副作用确定到什么程度**：确定已提交、确定未提交，或仍无法判断。

“后台工作已确认运行、还没结束”不是“是否启动都不知道”。不能因为尚无最终退出码就把所有后台工作当成失联的未知操作，并全面阻断后续工作。

### 7.2 最小阻断范围

结果不明时，框架要防止重复提交和冲突修改，但必须保留授权范围内的只读诊断、上下文查询和结果核验。

当前 `attempts.denial()` 在存在未决项时会拒绝非只读调用，原生 Bash Hook 未将只读查询单独分类；当前后台 Bash 还被标记为 UNKNOWN。[R3][R4] 下一轮应优先审计这条链路，避免“需要查询进程却连查询命令也被封住”。

不要通过“命令以 ps 开头”或模型声称 `read_only=true` 就随意放行。优先提供部署者批准的只读模板、受限查询工具或已验证的 Adapter 能力。无法安全确定冲突范围时可以保持保守阻断，但必须有实际可用的核验路径。

本轮不要求实现理解任意 Shell 的全能分类器。无法支持的情况应明确标为需人工核验，而不是假装已经自治恢复。

### 7.3 核验与解除

优先依据稳定操作 ID、远端查询、受管进程身份、输出文件和结构化运行时结果更新状态。身份必须匹配，旧代结果可以补充其原操作事实，但不能因此获得新代操作权限。

可信适配器能确定结果的，允许自动核验；代理可以发起查询并提交证据引用，但不能仅凭一句“我检查过了”解除防重放保护。

没有足够证据时继续保存未知状态，必要时通过 Yan 由授权操作者确认。人工确认是兜底，不应成为所有短暂断线的必经步骤。

### 7.4 不伪造执行保证

本地数据库先落盘不能自动保证远端命令只执行一次。真正的远端幂等依赖对端稳定身份、幂等接口或可核验的执行包装。

原生工具 Hook 是协作保护，不是同 UID 恶意程序的完整安全沙箱。已启动的外部进程也不能靠撤销 Session lease 自动回滚。

## 8. Task 完成：代理决定语义，框架验证协议

### 8.1 四个概念必须分开

**Task 完成**：用户交代的工作已经履行。

**业务结果**：支持／不支持假设、成功／失败、确定／不确定等实际结论。

**操作状态**：某次命令或 Job 是否结束、怎样结束。

**完成回执**：框架已接纳当前代理的有效完成申请。

同一个失败实验可能意味着“需要继续调试”，也可能意味着“验证任务已得到负面结论”，还可能仅是多步任务中的一个中间结果。框架不得从指标直接选择其一。

### 8.2 完成由谁发起

代理根据完整且最新的要求提交完成申请，附总结、证据和限制。用户也保留显式结束、取消或要求重新工作的控制权，但终态修改需要清晰 API，不能用普通 Resume 偷偷改写历史。

框架不因进程退出、CLI 打印 done、测试全绿、日志静默或全部 Job 结束而自动认定 Task 完成。

### 8.3 框架应检查什么

当前所有权与代际、当前要求版本、有效完成格式、并发 Hold/Cancel 的优先级、未决操作的处理，以及用户明确配置的机器验收契约。

代理决定结果解释，框架记录 `proxy-declared` 等来源。可选验证脚本通过也不等于所有业务结论都经系统证明。

没有配置验证脚本，不是默认缺陷；严禁为了“更安全”给所有 Task 强塞一个指标门槛。若用户指定必须通过某项检查，代理不能自行绕过或修改权威验收要求。

### 8.4 运行中的工作不必一律阻止所有任务完成

当前 `completion.py` 要求所有托管 Job 已有终态，所有 STARTED/UNKNOWN 命令已解除。[R5] 对“等待所有作业结束再汇报”合理，对“启动服务并交接”则可能过于严格。

本轮先审计此假设。如果要支持保留长期工作后结束 Task，必须是明确任务契约，并记录工作身份、后续责任方、观测和取消方式。未知副作用不能借“语义由代理判断”直接消失；无法做到可靠交接时保留既有保护并明确不支持。

这是一条契约兼容性检查，不要求本轮建设完整子工作流系统。

## 9. 上下文、提示词和交接

### 9.1 两类输入，不混来源

**框架固定协议**只说明角色、权限、来源可信度、所有权、回执、报告、接续、等待、交接和完成提交方式。

**Task 上下文**承载用户完整要求、追加指令、项目资料、验收要求、资源授权、既有工作、真实回执和代理笔记。

固定协议不得把任何任务变成巡检任务，也不得强制“先跑实验、失败后修复、成功后再跑”等科研专属流程。

### 9.2 上下文结构

保留现有按来源分区的设计：`operator_request`、`operator_updates`、`execution_contract`、`observed_state`、`agent_notes_unverified`、`completion_contract`。框架提醒应标明是观测，不伪装成新用户命令。[R6]

首代和接续代使用不同引导。原始任务要求不得被代理摘要取代；摘要方便恢复，不能删去授权限制、任务范围和验收要求。

历史记录很长时提供稳定引用、分页、游标和可继续读取的证据，而不是无限拼接进 prompt。关键身份、当前要求和未决操作不能静默丢失。敏感凭据不进入交接文本或公开仓库。

### 9.3 交接最小内容

当前目标与要求版本；已完成事项及证据；仍在执行的工作及身份；已尝试的方法与结果；未解问题；下一步建议；阻塞与授权边界。

“下一步建议”不是不可更改的指令。新代理可以依据新证据改变方案，不必继承旧代理的错误推断。

## 10. 人工介入和 AI 友好入口

### 10.1 能力面

Yan 应提供稳定、结构化的任务提交、状态查询、当前要求读取、事件／回执／会话记录分页、追加指令、Hold/Resume/Cancel、策略更新和受限核验入口。

Console 与 CLI/API 复用同一服务与回执，不各自实现一套状态机。外部 AI 不必截图理解界面才能知道系统是否在恢复。

### 10.2 指令状态必须诚实

区分已接收、已记录、已向代理交付、代理已确认读取，以及相关操作已执行。无法观测哪个阶段，就显示哪个阶段未知；不要为了界面完整伪造 ACK。

当前 `instruct_task` 的成功回执只表示指令已记录，明确 `analysis_executed=False`。[R7] 下一轮应审计后续交付路径，避免长 Session 一直不重新取上下文而错过修改。

读取确认也不能证明模型理解正确。要求版本用于防止旧上下文直接完成任务，不是读心术。

### 10.3 控制命令的边界

Hold 暂停代理继续推进；Cancel 终止该 Task 的继续授权；Resume 恢复明确暂停／等待的运行资格。自动恢复不得撤销用户控制。

这些命令默认不暗含杀死所有外部 Job。确需停止某项外部工作，走单独、可审计的明确操作。框架应展示旧代理权限撤销与实际进程回收的状态，而不是把异步清理伪装成瞬时全部结束。

### 10.4 Console 的重点

一个任务页应回答：用户要求是什么；当前谁负责；代理说在做什么；系统实际看到什么；为什么等／退避／隔离；下一次自动动作是什么；哪些命令未确认；有哪些仍在运行的外部工作；如何人工介入。

不能用一个绿色“运行中”覆盖所有信息。离线快照、陈旧观测、模型声明和真实回执必须可区分。

## 11. 核心框架、实例配置和运行状态分离

核心仓库保存通用协议、Controller、Adapter 接口、Yan、Console、测试和通用文档。

实例侧保存具体模型服务、节点、容器、项目目录、命令模板、任务书、允许资源和部署脚本。不得把公司环境、某篇论文、某个模型、某组 IP 和业务指标写死进核心。

运行状态保存到私有持久目录，不以 Git 提交代替状态同步。凭据独立管理，不进入审计内容、公共截图或代码。

开发迁移要先备份，明确 schema 兼容性；不能仅拉取源码却继续运行旧安装包。升级不得默默扩大已有 Task 的执行权限、预算或恢复策略。[R2]

保持当前小型本地控制面的边界，本轮不建设分布式多主控制系统。远程访问优先复用已有批准通道，不把控制端口裸露到公网。

## 12. 本轮实施范围与代码审计清单

### 12.1 保留已有正确设计

保留默认 Persistent、实验结果不触发 Session 故障、合作式换代、完整任务书、来源分区、代际所有权、持久命令回执、可选验收脚本、原生执行显式授权及真实/模拟测试范围标识。

不要把本次整理理解成全部推倒重写。

### 12.2 优先修复／补齐

| 范围 | 文件入口 | 目标 |
|---|---|---|
| 职责与术语 | `docs/ARCHITECTURE.md`、`docs/PROMPT_AND_LIFECYCLE_DESIGN.md`、`docs/RECOVERY_POLICY.md` | 消除框架替代理决定工作内容的旧表述，建立单一设计基线 |
| Prompt | `task_prompt.py` | 完整目标不被巡检化，内容判断归代理，系统约束不包含科研工作流 |

| 后台与未知状态 | `attempts.py`、`tool_hook.py`、`claude_process.py` | 区分已知运行中、返回丢失、停止和结果未明；验证通知时序 |

| 证据与兼容 | `store.py`、schemas、测试和部署文档 | 保留旧状态，迁移可核验，新增字段有来源和兼容策略 |

### 12.3 停止通知：审计项，而非预先定性的 P0

官方协议区分 completed/failed/stopped；特别说明 `reason=worker_restart` 的 stopped 不应被当作自身完成或失败。[E4]

当前 `observe_background` 已忽略带 reason 的通知，而普通 stopped 被归入 FAILED。[R3] 因此不能沿用“所有 stopped 都已经造成严重安全漏洞”的结论。

应在实际支持的 CLI 版本下分别测试完成、失败、主动停止、worker restart、通知丢失、通知重复、通知与 Hook 回执先后乱序及旧会话通知。保留原始状态和来源，依据实际保证决定结果确定性；不要为了改标签而破坏已正确的保护。

### 12.4 不要顺手扩大范围

不新增万能资源 Adapter、自动集群迁移器、全局业务进展分数或裁判模型。

对需要业务专属信息的需求，优先落到实例配置和代理上下文；对框架无法可靠观测的能力，明确范围，不包装成已经完成。

## 13. 验收：验证职责边界和执行效果

以下案例要形成“要求 → 代码路径 → 测试 → 证据”的可追踪矩阵。不是凑测试数量。

| ID | 场景 | 必须验证 |
|---|---|---|
| A01 | 连续大量普通测试失败 | 不隔离、不替代理宣布失败；后续工具仍可用 |
| A02 | 同命令同错误多次复测 | 可记录提示，不能强制换策略；代理可继续合理复测 |
| A03 | 很久没有运行证据更新 | 不声称没有业务进展，不仅凭此终止健康 Session |
| A04 | API 暂时失败、断流后恢复 | Persistent 有退避与请求限制；服务恢复后自动继续相同 Task |
| A05 | 健康慢操作超过 Session 年龄 | 不因年龄/grace 硬杀；新 Handoff 才正常换代 |
| A06 | CLI 自然结束或到回合上限 | Task 未完成时继续或进入明确等待，不以此宣告 Task 失败 |
| A07 | Controller 重启 | Task、指令、代际、回执、预算和外部工作身份保留，不重复启动 |
| A08 | 后台工作已确认运行 | 不错误地等同丢失启动结果；诊断和不冲突的已授权工作可继续 |
| A09 | 外部提交后回执丢失 | 不盲目再次提交；允许查询和核验；换代不绕过限制 |
| A10 | 核验能力不足 | 明确未知与人工介入原因，不伪造成功／失败／自动核验 |
| A11 | 后台通知乱序、重复、停止、worker restart | 事实不倒退、不覆盖成虚假终态；正确关联 Session 和调用身份 |
| A12 | 失败实验后代理选择继续 | 框架允许继续，不擅自完成 |
| A13 | 失败实验已回答任务，代理提交完成 | 无其他契约阻碍时接纳，不因指标差拒绝 |
| A14 | 所有测试成功但代理仍有任务 | 不因成功结果自动完成 |
| A15 | 无验证脚本的通用任务 | 允许正常完成；完成证据标明声明来源 |
| A16 | 用户明确配置必需验证脚本 | 脚本未满足时拒绝该完成申请，但不判 Session 故障 |
| A17 | 新指令到达与旧完成申请并发 | 要求版本校验生效，旧申请不吞掉新要求 |
| A18 | 用户 Hold/Cancel 与恢复定时器并发 | 用户控制优先；不会自动复活；外部 Job 的处理符合明确契约 |
| A19 | 旧代调用、伪造身份和权限扩展 | 受管接口拒绝，账本可追踪；不误伤无关进程 |
| A20 | 远程 UI/API | 持久化、交付、读取、执行等阶段不混淆；离线不显示实时 |
| A21 | 长任务上下文 | 完整要求和关键限制不静默截断；历史可按引用继续读取 |
| A22 | 升级旧数据与并行开发 | 不丢 Task，不扩大权限，不覆盖他人改动；迁移/回滚有证据 |

A12/A13 需要对相同的运行失败构造两种代理决策，验证框架尊重其角色而不是实现固定答案。A14 则验证相反方向。

测试报告分开列出：确定性单元/状态机测试；实际进程/CLI + 模拟模型；浏览器；真实 GLM/目标环境。Mock 决策成功只证明链路，不证明真实模型能正确研究或调试。

真实环境不可达时继续完成本地可做的实现和验证，明确未覆盖项。不得把未验收写为通过，也不要因为缺少生产凭据停掉所有可做工作。

## 14. 交给 Astra 的执行指令

你接手的是已有的 Sui Regulator，不是从零设计另一套项目。请按本规范完成一轮有实际代码、测试和文档证据的迭代，而不止输出建议。

先检查工作区、当前分支、远端提交和未提交改动，保留其他开发者的成果。读取本文件以及现有架构、恢复、提示词、执行与验收文档，识别哪些要求已经满足，哪些存在实现缺口。对已满足项增加或引用必要回归，不做无收益重写。

在仓库内建立一份规范性设计基线和一张简明实现映射表，随后优先修复第 12 节列出的阻碍自治、状态混淆和指令交付问题。实现选择服从第 0–11 节，特别是“内容判断归代理、运行可靠性归框架”。

不得把普通失败、重复失败、缺少新证据变成默认强制换代/停止规则；不得强制所有 Task 通过业务指标或固定验收脚本；不得用另一个 LLM 替代理决定工作内容。

不得以“自主”为由移除所有权、幂等、副作用核验和 Hold/Cancel 边界。未决状态要有可用排障路径；可安全自动核验时自动核验，证据不足时明确保留未知。

对 `stopped` 等协议行为先核对实际 CLI 版本和原始事件，不能把前一轮未经完整证实的 P0 结论当事实执行。测试通知时序，而不只看理想顺序。

按第 13 节完成有代表性的回归，重点证明同一业务失败可由代理选择继续或完成、健康慢任务不中断、断流后接续不重做、未决操作能诊断且不能盲目重放。不要把增加测试数量当作交付目标。

更新 Console 文案、schemas、部署迁移指南和项目说明，保持术语一致。README 面向人时可保持已有中文与适度世界观表达，但工程文档、API 和故障原因必须清楚，不额外强制做英文版。

能在当前授权环境内完成的工作自行推进，不为普通实现选择逐项要求用户确认。缺少新权限、凭据或存在不可逆风险时才明确指出边界；不得擅自新增权限或操作未知生产环境。

使用小而完整的提交。保留其他作者历史，不改写旧提交署名、不 force push；按当前协作分支方式提交和推送，出现远端并发变化先核对整合，不覆盖。提交作者如需标识模型，应真实记录本次实际执行者，不伪造参与者。

最终交付应包含：实际基线与新提交；已完成的职责边界修正；关键代码差异；要求到测试的映射和真实测试输出；迁移与启动方式；仍未覆盖的真实环境能力。必须区分“设计目标”“已经实现”“已验证”“待验收”。

本轮成功标准：司岁台不再因框架自己的业务判断打断合法工作，同时在 Session 故障、指令变更和执行不确定时仍能可靠承载同一个 Task。

- [E2：Temporal Tasks](https://docs.temporal.io/tasks)：借鉴运行任务故障与整体业务执行失败的区分；不声称实现 Temporal 的确定性重放，也不把其 Task 与本项目 Task 当成同一个对象。
- [E3：Kubernetes Probes](https://kubernetes.io/docs/concepts/workloads/pods/probes/)：借鉴启动、存活、就绪观测的职责分离；不照搬 Pod 重启策略来裁判 Agent 的工作质量。
- [E4：Claude Agent SDK TypeScript／SDKTaskNotificationMessage](https://code.claude.com/docs/en/agent-sdk/typescript#sdktasknotificationmessage)：核对后台通知的身份、状态与 worker_restart 语义；实际支持范围仍需锁定 CLI 版本验收。
- [E5：Claude Code Hooks](https://code.claude.com/docs/en/hooks)：核对执行前/执行后 Hook 的作用范围和失败处理；工具已经执行后的 Hook 不能撤销已经发生的外部副作用。

这些材料支持职责分离与协议细节；本文件中具体的产品边界、优先级和验收案例是针对司岁台需求提出的设计要求，不应冒充参考项目已经提供的保证。
